# 交付报告规范

ARTEX 是在授权范围内运行的 AI 自主渗透测试系统。交付报告面向负责修复的开发人员，每份只说明一个漏洞，讲清问题、实际结果和修复后的预期行为。报告整理只作用于交付正文。测试执行、工具权限和原始记录留存沿用现有流程。

## 排版

```markdown
# <漏洞名称>

CVSS 4.0：<分数>（<等级>）

向量：`<CVSS 4.0 Base 向量>`

## 漏洞描述

<受影响功能、触发条件和已观察到的业务影响>

已确认影响：<测试已经确认的业务后果>

触发位置：<已确认的页面及正常业务操作，或接口所属模块及页面入口的核实状态>

## 测试过程

- 测试角色：<实际验证使用的身份或权限>
- 预期行为：<系统按业务规则应有的表现>
- 实际结果：<测试中看到的结果>
- 未验证范围：<仅在影响结论时列出尚未确认的情况>

### Burp 复现包

<注明实际是否在 Burp 中验证；需要提供没有脱敏，可以直接复现的包>

### 攻击链路

<分项写出已确认的入口、校验缺口及实际影响>

### 复现脚本

<可以复现的poc，默认代理到burp，没开启burp也不报错>

## 修复建议

<开发应修改的行为，以及修复后的预期结果>

**修复后验证**

- <一条可单独核对的预期行为>
```

## 写法

- 用工程师给开发提缺陷的口吻。先写哪个功能有问题、什么条件下发生、用户实际看到了什么。同一结果只写一次。
- 标题使用漏洞名称。评分和等级根据保存的有效 CVSS 4.0 Base 向量计算。缺少有效向量时显示「待评估」。[FIRST CVSS 4.0 规范](https://www.first.org/cvss/v4.0/specification-document)
- 描述通常一两句。用平时和同事沟通的业务名称说明哪个功能出了什么问题、什么权限能遇到、已经看到了什么影响。尚未验证的范围直接写清。
- 在描述的结论之后另列「触发位置」。通过浏览器界面确认时，按界面顺序写页面、菜单或按钮和对应的常规业务操作。仅通过接口验证时，写接口所属模块、业务用途及前台入口的核实状态。只有确认没有前台入口时，才写隐藏接口。缺少记录时，写待核实。
- 测试过程以业务结果为主。报文长度、逐字节比较、内部序号、日志标签、文件具体属主和工具内部判定属于测试台账。
- 新生成的描述、测试过程和修复建议在保存时按事实字段整理。描述写已确认的后果，材料无法确认的情况放入测试过程的「未验证范围」。修复建议分别保存修复措施和验收预期。模型分工、发现合并关系和原文哈希留在详细报告。
- 同一事实字段可以续行。续行紧接上一行并缩进两个空格，预览和复制会保留续行中的事实。
- Burp 请求包只从漏洞绑定的 HTTP 流量证据生成，不让模型编造或改写。Authorization、Cookie、请求正文和业务参数均按采集值保留；请求头或 HTTP framing 为适配 Burp 做整理时，在压缩包说明中列明。没有绑定 HTTP 流量时明确标注，不生成占位请求。非 HTTP 测试注明不适用。
- Burp 复现包直接写在报告正文中，包含一条与漏洞核心结论对应的 HTTP 请求，可复制到 Burp Repeater。请求优先选择「漏洞验证」或「复核证据」，缺失时使用可解析的辅助请求。报文来源是 ARTEX 保存的 HTTP 请求行、请求头和完整请求正文，不代表 TLS/TCP 层逐字节抓包，也不是 Burp 项目文件。
- Python 复现脚本只从该漏洞绑定的完整「漏洞验证」、「复核证据」或辅助 HTTP 请求生成，不执行详细报告中的任意代码，不补造请求或利用载荷。请求中的认证信息和正文按采集值保留；若请求头或 HTTP framing 为重放需要调整，脚本只重算 Content-Length 并移除 Transfer-Encoding。
- Python 脚本使用标准库。默认不配置代理并直连目标；设置 `BURP_PROXY=http://127.0.0.1:8080` 后才经 Burp 发送。Burp 未启动且未设置该变量时，脚本仍按直连方式运行；显式启用代理但 Burp 不可用时，脚本会显示连接错误且不会静默改走直连。HTTPS 拦截可通过 `BURP_CA_CERT` 指定 Burp CA PEM 证书，不关闭证书校验。
- Python 一项可以同时引用已有的修复回归用例和预期结果。没有完整的验证/复核请求时不生成重放脚本，并按实际情况标注。
- 历史报告如果只有 HTTP 复测示例，交付稿会提示核对实际执行情况。报告会保留旧版定级说明中的权限条件、否定性观察和未验证的范围。
- 攻击链路概括入口和业务影响。存在独立观察时分别概括，保留原有的因果关系和验证边界。
- 黑盒报告用受影响的功能或接口、测试角色和实际表现帮助开发定位。源码位置是可选信息，有已核实的文件和行号时才填写。
- 修复建议写清应检查的校验点，以及修复后正常访问和受限访问应分别怎样表现。
- 黑盒测试已确认缺陷行为时，可以按业务环节提出修复。列出应应用同一授权规则的环节，并明确有权限和无权限时各自的验收结果。源码位置可以待查。
- 原稿有明确复测标准时，修复建议下列出修复后可核对的结果。保留正常操作是否继续成功、受限操作应如何被拒绝等预期。

## 交付验收

- 任务结束、发现登记和报告保存分别核对。正式交付前确认详细报告和交付报告均已保存、CVSS 4.0 评分有效、证据版本一致。
- HTTP 分项的复现章节缺少完整报文时，明确标记缺项并保留为草稿。流量条数仅用于核对证据。

## 预览与复制

任务详情的「报告」覆盖该任务的全部已登记发现。系统先按已登记发现显示草稿，随后以已保存的交付报告替换对应分项。任务完成或到达停止时间后，所有分项均通过交付检查时，才提供「复制交付报告」。其他情况下可用「复制报告草稿」，复制文本会保留草稿标识及缺项。没有登记发现时也可复制当前汇总。

顶部目录列出编号、名称和等级，点击名称可跳到对应正文。已保存的分项使用 CVSS 等级，按登记记录出具的分项使用登记等级。目录和正文标题沿用同一个系统漏洞编号，便于在页面或复制的 Markdown 中搜索。已保存分项中的 Burp 请求包和 Python 复现脚本包含在页面及复制的 Markdown 正文中。报告与测试记录版本不一致时，会在对应漏洞下提示核对。

任务完成状态和报告保存状态分别显示。任务报告页分别统计详细报告和交付报告，标明未保存与读取失败的分项。已保存的详细报告可从对应分项打开。

HTTP 分项的「Burp 复现包」须包含原始 HTTP 请求代码块和已记录的 Burp 验证状态。代码块包含请求行、请求头和必要的请求正文。示例请求和二进制正文的 Base64 留存都无法通过直接复制请求的检查。非 HTTP 分项须注明 Burp 不适用。

打开漏洞详情的「交付报告」，左上角可复制报告正文。Burp 小节显示原稿记录的验证状态、报告和页面加载时的附件证据版本，并展示可复制到 Repeater 的请求。Python 小节显示由绑定请求生成的重放脚本，以及原稿记录的回归用例位置和预期结果。有额外的复测标准时，可在「修复后验证」查看。报告与测试记录版本不一致时，页面和复制的 Markdown 都会提示交付前先核对。
